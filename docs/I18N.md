# Internationalization

Status: a plan, reviewed twice (feasibility against the code, and security against the invariants). Nothing is built. It comes from a run of the i18n persona (`personas/i18n.md`, Japanese and Arabic) and a reading of the code.

## Claim

A developer who works in a language other than English should be able to use sitrep without it breaking or misleading them about their own text, should be told what to expect, and should be able to see the screens they look at every minute in their own language. Today the first part mostly holds, the second does not, and the third does not exist.

## What holds already

The persona found the layout sound: with Japanese, fullwidth, emoji, combining marks and Arabic text, no row was wider than the window at 110 and 60 columns in Cards, Table or Wall, and an ellipsis never fell inside a character. The locale never changes a frame: `textsafe` pins `runewidth` to narrow ambiguous characters, and `ansi.StringWidth` uses its own tables. All of this stays.

There are two width engines, though. The dashboard measures with `ansi.StringWidth` (grapheme aware). `textsafe.Width` and `textsafe.Fit`, which `sitrep ls` and the status line use through `internal/render`, use `runewidth`, which is not, and the two can disagree on emoji sequences. Piece 3 makes `Fit` and `Width` agree with the dashboard.

## What is missing

1. **The summaries.** The summarizer prompt (`internal/hook/summarize.go`) names no language, and no document says what language Objective, Progress and Now come out in.
2. **Text handling.** The filter (`matches` in `internal/tui/views.go`) uses `strings.ToLower`, so `café` typed as one character does not find the same word stored as `e` plus a combining accent, and `full` does not find `ｆｕｌｌ`. The limits in `textsafe` (200 characters for a field, and the queue item cut) count code points, so a cut can drop a combining accent or a skin-tone modifier. Zero-width joiners are removed with the other format characters (invariant 1), so `👨‍👩‍👧` shows as `👨👩👧`.
3. **A statement.** The README does not say that UTF-8 text is shown as written, that aliases are ASCII only, that the interface is English only, or what happens to joiners and bidi controls.
4. **The program's own words.** All of them are English, and some are built by joining words (`Inbox: 3 items, next: ...`, `2 queued: ...`), which a translation could not reorder.

## What is out of scope

- **Non-ASCII aliases.** The alias grammar (`state.ValidAlias`, invariant 3) is what makes an alias safe to print and impossible to mistake for a flag, an item number or another session's id. A Unicode alias brings look-alike letters and mixed scripts into that. Keep it ASCII and say so. A person who wants a name in their language has the Objective, which is free text.
- **Translating machine formats.** `ls --json`, the hook protocol, the state files, `sitrep.conf` names, command and flag names, completion and the `docs/` pages stay English. A translation is a display, never a format: the notes file keeps the keys `Objective`, `Progress` and `Now`, and the JSON keeps `working` and `waiting`.
- **A left-arrow cursor in the prompts.** It was found in the run and is real, but it is not about language. It goes to the roadmap, not here.
- **Right-to-left layout.** Arabic and Hebrew text is shown in logical order, and the terminal decides how to draw it. The dashboard stays left to right, and bidi controls stay removed (invariant 1).

## Plan

Five pieces, in this order. Each can be released alone, and each is one or two commits.

### 1. Say it (docs only)

A short paragraph in the README under Settings (and a line in `docs/SETTINGS.md`) saying: text in any language is shown as written; double-width characters and emoji are counted in the layout; aliases are ASCII; the interface and the help are English only (until piece 5); joiners inside emoji sequences and bidi controls are removed on purpose; strong right-to-left letters can reorder the neutral characters next to them in terminals that do bidi; and what language the summaries come out in (piece 2). Until piece 2 is built, test once what Claude does with a Japanese session before the sentence is written.

### 2. The language of the summaries

It has the best value for the cost, so it goes first.

1. The summarizer prompt gets one fixed sentence: "Write the three lines in the language of the user's messages in the transcript. Keep the words Objective, Progress and Now as written." The keys stay in English because `field()` parses them: a summary whose keys were translated is dropped without a word, so a test pins the sentence about the keys.
2. `SITREP_SUMMARY_LANG=<tag>` overrides it with a language tag (`en`, `ja`, `ar`, `pt-BR`). The value goes into a prompt, so it is parsed with `language.Parse` (`golang.org/x/text/language`, version 0.3.8 or later, since earlier ones have advisories) and only the canonical tag it returns is used, inside a fixed template sentence ("Write the three lines in the language with the tag X."). A name such as "English", a long string or anything that does not parse is ignored and the default applies. The check is made in the summarizer, next to the prompt, because the value reaches it from `sitrep.conf` and from the environment the hooks run in, which is also what `z.Env` carries. A string such as `ignore-rules` is not a tag, and a test says so.
3. The limits in the prompt (80 and 120 characters) count characters, and CJK text says more per character, so they stay. The stored bound is 200 code points, as now, and the summary still passes through `Sane`.
4. Fits the design: no new state, no new network use, nothing new to read. It costs a few tokens per summary. It changes what users with non-English prompts see after the update, which is the point, and the release notes say so.
5. Tests with the runner's fake: the prompt holds the sentences; a valid override gives its canonical tag; an invalid one changes nothing. What Claude then writes is not tested (the fixture has no Claude), and a human checks one real run in Japanese before release.

### 3. Text handling

1. **The filter matches what a person sees.** Normalize the query and every field to NFKC and fold the case (`golang.org/x/text/unicode/norm` and `cases`) before comparing, so precomposed and decomposed forms match and fullwidth Latin matches plain Latin.
   - The normalized text is used only for the comparison. It is never shown, stored or cached in a field that is rendered, since NFKC turns a fullwidth solidus into `/` and a circled digit into `(1)`. Any cache on `Session` is private and is not a `textsafe.Text`.
   - NFKC can expand one character to 18 (U+FDFA). That is bounded by the field limits, but the cost is real: 3,000 sessions with seven fields on every keystroke is about a million characters. Measure it with the 3,000 session fixture. An ASCII fast path (no normalization when both sides are ASCII) and a cache of the normalized fields, rebuilt when the session data changes, are the two answers. If it is still slow, debounce the filter.
   - `cases.Fold` is not safe for concurrent use, so each call makes its own, fixed to `language.Und`, never to `LANG`. `ß` against `SS` stays unmatched, and what Turkish `İ` gives is pinned by a test.
   - `state.Resolve`, `ParseID` and the alias lookup stay byte-exact. Normalization is for the filter and nothing else.
2. **Cuts fall between grapheme clusters.** `textsafe.cut` and the queue item cut keep at most N code points today. They stop at the last cluster boundary at or below N (`uniseg`, which becomes a direct dependency, so its `// indirect` mark in `go.mod` goes, or `go mod tidy -diff` in `make test` fails).
   - The limit stays a number of code points, so the storage bounds do not change, and a field can end a few code points short.
   - A first cluster that is longer than N (a run of 10,000 combining marks) is cut inside, so the bound always holds: a test pins it.
   - `CleanMarked` decides that a field was cut by asking for N+1 and testing whether more than N came back. With cluster cuts, a cut can return N or fewer, and the ellipsis would be lost silently. The cut function reports whether it truncated, and the marker follows that.
3. **One width engine.** `textsafe.Width` and `Fit` use `ansi.StringWidth` and its truncation, as the dashboard does, and the `runewidth` pin stays only where `runewidth` is still used. Tests compare the two on the persona's cases (ZWJ sequences, flags, skin tones, combining marks, fullwidth), and the existing no-row-wider-than-the-window tests keep passing.
4. **Joiners (a decision).** Options: (a) leave the removal and document it, as piece 1 does; (b) keep U+200D and U+FE0F only inside an emoji sequence that `uniseg` sees as one cluster. Option (b) shows the family emoji whole, but it loosens the filter that invariant 1 relies on, widths of such sequences differ between terminals (some draw one glyph, some three, while the layout counts two), and the hostile-input persona would have to run again. Both reviews of this plan favour (a), and so do I. The loss is cosmetic and the risk is not.
5. Tests: the persona's cases as a table (decomposed `café`, fullwidth, `STRASSE`, the cut at 199 characters plus an accent, a skin-tone sequence, a long run of marks), and the hostile fixture timed before and after.

### 4. Split the state label from the state word (no translation)

This is the hidden first step of piece 5, and it can ship alone. `StateLabel` is today both the text shown ("waiting 3m", "idle? 12m", "ended 8m") and a value the program tests: `snapshot.go` checks it for the prefixes `idle?` and `ended`, `live.go` builds it, `tui/data.go` validates the words, the views branch on `State == "working"`, and the demo data tests `label[:5] == "idle?"`. A translated label would break all of these.

1. The state is a code (`working`, `waiting`, `ended`, `running`, `idle`) and an age. Code that decides things uses the code and the `Idle` flag. The display text is built in one place from the code and the age, in English at first, so this piece changes no output and the golden files prove it.
2. `ls --json` keeps the same fields and the same English words (it is a versioned format: `docs/JSON.md`). Check whether `state_label` is in the format and keep it as it is.
3. The filter searches the display text, as it does today, and also the English word, so that a person who types `waiting` finds a waiting session whatever the language.

### 5. The program's own words

The goal is a small catalog, not a translation of everything. What is shown to a person is ranked by how often it is seen.

1. **Every minute:** the tab names, the table column headers, the state words, the summary line, the hint bar and the status bar, the queue and inbox lines, and the filter and name prompts.
2. **The first day:** the `?` help and its legend (which contains the state words and tab names), the demo banner, the detail view, the status line's labels, the colour tool's prose, the prune and jump messages.
3. **Rarely, and left in English in the first release:** errors, `sitrep help` and each command's `--help`, the setup messages, completion, and the answers the hooks give. The hook answers go to Claude Code and to Claude, and `sitrep ls` is read by scripts, so the hooks never load a catalog (invariant 4), and `SITREP_LANG` for the hooks does not matter. A person who meets an error can paste it into a search, and a translated one is harder to find.

How:

1. A package `internal/i18n` with `T(key, args...)`. English is the source and the fallback: a key with no entry in the chosen language gives the English text, so a missing translation is never an empty screen. Catalogs are embedded JSON files (`go:embed`), one per language, loaded only for the language in use, and only by the dashboard, the status line and the commands that print for a person. No network, no state.
2. **The language is chosen from a list.** `SITREP_LANG`, then `LC_ALL`, `LC_MESSAGES`, `LANG`; the language part of the value (`ja_JP.UTF-8` is `ja`) is looked up in the list of shipped languages, and `C`, `POSIX` or anything not in the list means English. The value never becomes part of a file name. A catalog that fails to parse, or a panic in loading, gives English (`recover` at the load), and the shipped catalogs are parsed in a test at build time.
3. **The result is a `textsafe.Text`.** `T` returns a `Text`, made by a constructor in `textsafe` that the loader uses on the catalog text (a `Strip` at load time), so the catalog cannot bring a control, format or bidi character, or an escape, into the TUI, whatever a test says. A translation cannot hold a bidi mark: this is on purpose.
4. **Placeholders** take numbers and `textsafe.Text` only. The substitution is one pass over the template, never a series of replaces, so a hostile alias or Objective that contains `{next}` is not expanded again. Catalog text never goes to `fmt.Sprintf`. `tui.Session` holds plain strings that were cleaned when loaded (`data.go`), so the first commit of this piece decides how they are passed: retype the fields, or convert at the call, and I recommend converting at the call with one helper, since retyping `Session` touches every view.
5. **Plurals and word order.** A message is a whole sentence with named placeholders, never a joined fragment, and a message with a count has one text for each plural category of the language (English two, Japanese one, Arabic six). The code that joins words today becomes whole messages first, in English, with no change in output. The places are not only `summary()`: the short and the full form of the summary line (`fitSummary`), `"   sort: "+name`, the queue and inbox lines, and `queue.go:746`, which builds "the <name> is empty" from a lowercased name and cannot be translated. Each variant is its own message.
6. **Layout.** The code measures widths, but a few numbers assume the English header widths (the budget constants 13 and 22 in the Table, `detailLabel`, the label column of the status block). They are checked by the no-row-wider-than-the-window tests at 60 and 110 columns for each shipped language, and a hint that does not fit is left out as it is now, so a long translation costs a hint, not a broken frame. The readme screenshots and the demo data are English and stay so, and the screenshot tool sets `SITREP_LANG=en`.
7. **Tests.** The scenario harness (`clitest`) and the other tests that draw screens pin `SITREP_LANG=en` and clear `LC_ALL`, `LC_MESSAGES` and `LANG`, so the golden files do not change with the machine. A catalog test per language checks the keys, the placeholders and that no message holds a control or format character. A screen test per language draws each tab and checks the widths. The tests that match on English text stay valid because they run in English.
8. **A rule for the future.** Every new user-facing string that a person reads on a screen goes through `T`, and `AGENTS.md` says so. A test that finds string literals in the shipped screens is not worth its false alarms: review catches it, as for the other rules.

Which language first is the user's choice (see the questions). One reviewed translation proves the mechanism, and a catalog nobody can read is not worth shipping. A contributor can add a language by copying the English file, and `CONTRIBUTING.md` says how.

## What it costs

Piece 1 is words. Piece 2 is a sentence of prompt, a setting, one dependency (`golang.org/x/text/language`) and tests. Piece 3 is a few functions and tests, and adds `norm` and `cases` from the same module and makes `uniseg` direct. Piece 4 is a refactor of `snapshot`, `live` and the dashboard with no change in output. Piece 5 is the big one: a small package and a change of most of the user-facing strings in the dashboard (`views.go`, `model.go`, `queue.go`, `wall.go`, `detail.go`, `colors.go`, `prune.go`, `jump.go`, the `?` legend) and the status line, with the golden files as the check that English did not change. The count of those strings was not made; the first commit of piece 5 counts them, and the cost is restated then. After it, every user-facing change carries a catalog entry.

## Risks

- The filter's per-keystroke cost on a large fleet (measured before it is kept), and a hostile field that normalization expands.
- A translation that is longer than the English and breaks a fixed column. The width test per language is the answer.
- A language file that nobody can maintain. Ship one, and say in the README that the others are not there.
- East Asian terminals that draw `●`, `▶` and the box characters two columns wide (the "ambiguous width" option of iTerm2 and others). The persona could not test it, since tmux does not change it. A person with such a terminal would see misaligned rows, and the setting that fits (a switch that counts these as two) is not designed here: test it on a real terminal before deciding.
- Claude Code's own interface is English, and the user's session language is set elsewhere. Matching sitrep to `SITREP_LANG` and not to Claude's setting is deliberate: sitrep cannot read it, and it should not read `~/.claude/settings.json` for this.

## Questions for the user

1. Which language first for piece 4, given that someone has to review it? Japanese was the persona's choice, and German or French are the cheapest to read for a reviewer.
2. Joiners: leave them removed and document it (recommended), or keep them inside emoji sequences?
3. Should the summaries follow the language of the prompts by default (recommended), or only when `SITREP_SUMMARY_LANG` is set? (It changes what current users see.)
4. Is leaving errors, `--help`, the setup messages and the hook answers in English in the first release acceptable?
5. Is the new dependency `golang.org/x/text` (version 0.3.8 or later, for `language`, `norm` and `cases`) acceptable? Pieces 2 and 3 both need it.
6. Piece 4 changes no output but touches the core. Are you content for it to be built and released before any translation exists?
